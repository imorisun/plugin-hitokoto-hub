# 批量删除非最优句子功能全面重构方案

## Context

用户反馈:当前功能已实现刷新操作,但执行过程中出现服务器内部错误。要求按照软件工程最佳实践全面重构,包括根因定位、健壮架构设计、错误处理、日志记录、边界条件覆盖、代码规范和测试。

### 根因分析

通过对完整调用链路的静态分析,确认服务器内部错误的根本原因有 6 个层面的缺陷:

| # | 缺陷 | 位置 | 表现 |
|---|---|---|---|
| 1 | 端点层无 `onErrorResume` | `SimilarityCheckConsoleEndpoint.deleteNonOptimal` L188-192 | 任何服务层异常都传播为 500 HTML 错误页,前端 `e?.response?.data?.message` 取不到值 |
| 2 | 服务层无全局错误兜底 | `SimilarityCheckServiceImpl.deleteNonOptimalSentences` L122-139 | `fetchAllSentences` / `collectNonOptimalNames` 任一抛异常直接传播 |
| 3 | 响应格式非结构化 | 端点返回 `Map.of("message", ..., "deleted", count)` | 成功有 `deleted`,失败时 Spring 默认 HTML,前端解析不一致 |
| 4 | 单条删除计数丢失 | `deleteSentencesInBatch` L274-282 | `switchIfEmpty(Mono.empty())` 让"未找到"被静默吞掉,无法区分"成功删除"和"未找到" |
| 5 | 日志覆盖不全 | 全链路 | 缺少"获取日志失败""获取句子失败""收集待删除名称失败"等关键节点日志 |
| 6 | 端点无单元测试 | 无 `SimilarityCheckConsoleEndpointTest` | 端点错误处理逻辑无回归保护 |

**与项目惯例的对比**:项目中其他端点(`SentenceSubmissionConsoleEndpoint`、`AiGenerateLogConsoleEndpoint`、`SimilarityCheckConsoleEndpoint.getLog`)都使用 `onErrorResume` 将异常转换为结构化 HTTP 响应,唯独 `deleteNonOptimal` 缺失这层保护。

### 预期结果

- 在各种边界条件下(无日志/无句子/无相似对/单条删除失败/句子被并发删除/数据访问异常)均不出现 500 错误
- 业务正常路径返回结构化 `BatchDeleteResult`,技术异常返回 500 + 结构化错误体
- 前端可通过统一字段(`deleted`、`message`)解析响应,无需区分成功/失败的不同结构
- 服务层有完整日志链路,便于问题定位
- 端点层有单元测试覆盖,防止回归

## 当前状态分析

### 现有调用链路

1. **端点** `SimilarityCheckConsoleEndpoint.deleteNonOptimal` (L188-192):
   ```java
   return similarityCheckService.deleteNonOptimalSentences()
       .flatMap(count -> ServerResponse.ok()
           .bodyValue(Map.of("message", ..., "deleted", count)));
   ```
   - 无 `onErrorResume`,异常传播为 500

2. **服务** `SimilarityCheckServiceImpl.deleteNonOptimalSentences` (L122-139):
   - 链路:`getLatestSuccessLog` → `fetchAllSentences` → `collectNonOptimalNames` → `deleteSentencesInBatch`
   - 仅有 `switchIfEmpty(Mono.just(0))` 兜底无日志场景
   - 其他环节无 `doOnError` / `onErrorResume`

3. **批量删除** `SimilarityCheckServiceImpl.deleteSentencesInBatch` (L268-286):
   - 单条 `client.delete` 有 `onErrorResume` 跳过(项目硬约束)
   - `switchIfEmpty(Mono.empty())` 让"未找到"被静默吞掉
   - `.reduce(0, Integer::sum)` 只统计成功数,无法区分失败原因

### 关键约束(从 memory 和代码探索确认)

- **硬约束**:批量删除非最优句子必须操作所有数据;单条失败跳过不中断;不修改 `SimilarityCheckLog`;不修改 `SentenceReconciler`;不修改算法层
- **项目约定**:错误响应用 `Map.of("message", ...)`;DTO 用 record 风格放 `service/dto/`(参考 `CategoryStats`);端点测试用纯 Mockito mock
- **调用方确认**:`deleteNonOptimalSentences` 仅 4 处引用(接口/实现/端点/测试),修改签名安全
- **前端兼容**:前端依赖 `data.message` 和 `data.deleted` 字段,必须保留

### 测试基础设施

- `MockExtensionClient`:内存 fake,支持 `listAll`/`fetch`/`delete` 等
- `TestFixtures`:`sentence()`/`successLog()` 工厂方法
- 端点测试参照 `SentenceConsoleEndpointTest`:纯 Mockito mock + `StepVerifier`

## 提议变更

### 变更 1:新建 `BatchDeleteResult` DTO

**文件**:`src/main/java/top/puresky/hitokotohub/service/dto/BatchDeleteResult.java`(新建)

**理由**:统一成功/失败的响应结构,与 `CategoryStats` 的 record 风格一致,保留前端依赖的 `deleted`/`message` 字段,新增 `total`/`failed` 提升可观测性。

```java
package top.puresky.hitokotohub.service.dto;

import io.swagger.v3.oas.annotations.media.Schema;

/**
 * 批量删除非最优句子的结果。
 *
 * <p>字段命名与 SentenceConsoleEndpoint.BatchCreateSentenceResult 的
 * total/success/failed 三元结构对齐,并保留前端依赖的 deleted / message。
 *
 * @param total    候选删除总数
 * @param deleted  成功删除数
 * @param failed   失败数(含未找到、删除异常)
 * @param message  汇总消息(前端 toast 显示)
 */
@Schema(name = "BatchDeleteResult")
public record BatchDeleteResult(
    @Schema(description = "候选删除总数") int total,
    @Schema(description = "成功删除数") int deleted,
    @Schema(description = "失败数(含未找到)") int failed,
    @Schema(description = "汇总消息") String message
) {
    public static BatchDeleteResult empty(String message) {
        return new BatchDeleteResult(0, 0, 0, message);
    }

    public static BatchDeleteResult of(int total, int deleted, int failed) {
        return new BatchDeleteResult(total, deleted, failed,
            String.format("批量删除完成:候选 %d 个,成功 %d 个,失败 %d 个",
                total, deleted, failed));
    }
}
```

### 变更 3:重构 `SimilarityCheckServiceImpl`

**文件**:`src/main/java/top/puresky/hitokotohub/service/impl/SimilarityCheckServiceImpl.java`

**3.1 重构 `deleteNonOptimalSentences`** (L122-139):
- 添加 `doOnError` 日志覆盖 `fetchAllSentences` 和 `collectNonOptimalNames` 失败场景
- `switchIfEmpty` 返回 `BatchDeleteResult.empty(...)`
- 各业务分支(无句子)返回 `BatchDeleteResult.empty(...)`

```java
@Override
public Mono<BatchDeleteResult> deleteNonOptimalSentences() {
    return getLatestSuccessLog()
        .flatMap(latestLog -> {
            String algorithm = latestLog.getSpec().getAlgorithm();
            double threshold = latestLog.getSpec().getThreshold();
            String logName = latestLog.getMetadata().getName();
            log.info("批量删除:开始处理,log={}, algorithm={}, threshold={}",
                logName, algorithm, threshold);
            return fetchAllSentences()
                .doOnError(e -> log.error("获取句子列表失败, log={}", logName, e))
                .flatMap(sentences -> {
                    if (sentences.isEmpty()) {
                        log.info("批量删除:无句子可处理, log={}", logName);
                        return Mono.just(BatchDeleteResult.empty("无句子可处理"));
                    }
                    return Mono.fromCallable(() ->
                        collectNonOptimalNames(sentences, algorithm, threshold))
                        .subscribeOn(Schedulers.boundedElastic())
                        .doOnError(e ->
                            log.error("收集非最优句子名称失败, log={}", logName, e))
                        .flatMap(names -> deleteSentencesInBatch(names, logName));
                });
        })
        .switchIfEmpty(Mono.fromSupplier(() -> {
            log.info("批量删除:无 SUCCESS 状态的检查日志,跳过");
            return BatchDeleteResult.empty("无相似度检查日志,请先触发检查");
        }));
}
```

**3.2 重构 `deleteSentencesInBatch`** (L268-286):
- 签名增加 `logName` 参数(仅用于日志)
- 用 `defaultIfEmpty(false)` 区分"未找到"和"成功删除"
- 用 `reduce(new int[]{0, 0}, ...)` 累加 `[deleted, failed]`
- 返回 `BatchDeleteResult.of(total, deleted, failed)`

```java
private Mono<BatchDeleteResult> deleteSentencesInBatch(Set<String> names, String logName) {
    int total = names.size();
    if (total == 0) {
        log.info("批量删除:无非最优句子待删除, log={}", logName);
        return Mono.just(BatchDeleteResult.empty("无非最优句子需要删除"));
    }
    log.info("批量删除:共 {} 个待删除, log={}", total, logName);

    return Flux.fromIterable(names)
        .flatMap(name -> client.fetch(Sentence.class, name)
            .flatMap(s -> client.delete(s)
                .thenReturn(true)
                .onErrorResume(e -> {
                    log.warn("删除句子 {} 失败: {}", name, e.getMessage());
                    return Mono.just(false);
                }))
            .defaultIfEmpty(false), 16)
        .reduce(new int[]{0, 0}, (acc, ok) -> {
            if (ok) acc[0]++; else acc[1]++;
            return acc;
        })
        .map(counts -> {
            int deleted = counts[0];
            int failed = counts[1];
            log.info("批量删除完成:log={}, total={}, deleted={}, failed={}",
                logName, total, deleted, failed);
            return BatchDeleteResult.of(total, deleted, failed);
        });
}
```

## 关键设计权衡

### 1. 错误处理层级:端点层兜底,服务层日志

- **端点层**:`onErrorResume` 统一将异常转换为 500 + 结构化错误体
- **服务层**:`doOnError` 记录日志但不吞异常,让异常传播到端点
- **资源访问层**:不增加捕获,异常自然传播
- **理由**:遵循项目现有惯例(其他端点都用 `onErrorResume`),职责清晰

### 2. 为什么不引入 `@ControllerAdvice` 全局异常处理器

- 项目所有端点都用方法内 `onErrorResume` 处理,引入全局处理器会破坏约定
- 全局处理器无法针对不同端点给不同响应(404 vs 500)
- 保持最小改动

### 3. `BatchDeleteResult` 放在 `service/dto/` 而非端点内嵌类

- `CategoryStats` 已在 `service/dto/` 建立 record 风格先例
- `BatchDeleteResult` 是 service 接口契约的一部分(`Mono<BatchDeleteResult>`),跨层传递,独立文件更合适
- `SentenceConsoleEndpoint.BatchCreateSentenceResult` 是内嵌类,因为它仅在端点内使用

### 4. `IllegalArgumentException` 在批量删除场景映射 500 而非 404

- `getLog` 的 `IllegalArgumentException("日志不存在")` 语义是"请求的资源不存在" → 404
- 批量删除场景下 `IllegalArgumentException` 可能来自算法层(参数非法),代表"程序异常" → 500
- 避免误导前端进入"资源不存在"的 UI 分支

### 5. 不缓存 `performCheck` 计算结果

- `SimilarityCheckLog.similarPairs` 有 `MAX_STORED_PAIRS=500` 截断,复用会导致漏删
- `performCheck` 时与 `deleteNonOptimalSentences` 时句子集合可能已变化,复用会误删
- 已有倒排索引优化(n≥500 自动启用),O(n²) 在 n<1000 时耗时可控
- 缓存会引入"日志/句子集合一致性"问题,违反"不要过度工程化"

### 6. 不返回 `failedNames` 列表

- 当前前端无重试 UI,返回 `failedNames` 会增加响应体大小且无消费者
- 保留扩展空间:未来可加 `failedNames` 字段,向后兼容

## 异常处理策略矩阵

| 异常来源 | 处理策略 | 理由 |
|---|---|---|
| `client.fetch` 返回 empty(句子已被并发删除) | 计入 `failed`,继续 | 数据竞态,需可见 |
| `client.delete` 单条抛异常 | `onErrorResume` 跳过,计入 `failed`,继续 | 项目硬约束:单条失败不中断 |
| `client.listAll(Sentence)` 失败 | `doOnError` 记日志,传播到端点 → 500 | 数据访问失败,整体无法继续 |
| `client.listAll(SimilarityCheckLog)` 失败 | 传播到端点 → 500 | 同上 |
| `collectNonOptimalNames` 算法异常 | `doOnError` 记日志,传播到端点 → 500 | 算法 bug 不应静默 |
| `getLatestSuccessLog` 返回 empty | `switchIfEmpty` 返回 empty result | 业务正常路径 |
| `fetchAllSentences` 返回 empty list | flatMap 内返回 empty result | 业务正常路径 |
