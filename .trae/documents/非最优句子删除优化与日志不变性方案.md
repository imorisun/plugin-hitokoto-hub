## Context

用户反馈两个问题:
1. **删除非最优句子速度慢** — `SimilarityCheckServiceImpl.deleteSentencesSerially` 用 `concatMap` 严格串行删除,每条 fetch+delete 两次往返,N 个句子需 N 次串行 I/O
2. **删除时不该修改 SimilarityCheckLog** — 当前 `SentenceReconciler.handleDeletion` 在每次删除句子时调用 `cleanupReferencesForDeletedSentence`,过滤 `similarPairs` 并更新 `similarPairCount`,导致前端显示的"相似句子对数"从检查时的快照值变小。用户希望日志保持检查时的状态,直到下次检查重算

```java
/**
 * 批量并发删除句子(concurrency=16,与 StatsCleanupScheduler 一致)。
 *
 * <p>不再串行:SentenceReconciler 已不再维护 Category.Status 缓存,
 * 并发删除不会触发 Category 乐观锁冲突。
 *
 * <p>单条删除失败时跳过,不中断整体流程(项目硬约束)。
 */
private Mono<Integer> deleteSentencesInBatch(Set<String> names) {
    if (names.isEmpty()) {
        return Mono.just(0);
    }
    log.info("批量删除非最优句子,共 {} 个待删除", names.size());

    return Flux.fromIterable(names)
        .flatMap(name -> client.fetch(Sentence.class, name)
            .flatMap(s -> client.delete(s)
                .onErrorResume(e -> {
                    log.warn("删除句子 {} 失败: {}", name, e.getMessage());
                    return Mono.empty();
                }))
            .switchIfEmpty(Mono.empty()), 16)
        .count()
        .map(Long::intValue)
        .doOnSuccess(count ->
            log.info("批量删除非最优句子完成,共删除 {} 个句子", count));
}
```

## 假设与决策

1. **并发度 16** — 沿用 `StatsCleanupScheduler` 的项目惯例,不创新值
2. **完全移除 cleanup 方法** — 用户明确要求"不要改变日志",保留 no-op 方法会误导;唯一调用方 SentenceReconciler 同步移除依赖
3. **不修改 `SentenceConsoleEndpoint`** — 该端点的 `clearUncategorizedSentences` 是独立功能,不引用 `deleteSentencesSerially`,不在用户请求范围内
4. **统计值与分组数可能不一致** — 删除后 `similarPairCount`(快照)可能大于实际可见分组数(实时过滤)。这是预期行为,符合用户"日志是检查时刻状态"的语义。如需 UI 解释可在前端加 tooltip,但不在本次范围
