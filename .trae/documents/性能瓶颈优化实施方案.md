# 性能瓶颈优化实施方案

## Context

上一轮代码质量评估识别出 8 处性能瓶颈(P-1 ~ P-8)。本方案聚焦性能维度,实施 7 项高价值优化(P-4 的 `.block()` 在 `boundedElastic` 内可接受,本次不动)。优化后预期:

- Overview 接口查询数从 `3+3C` 降至 `3`(C=20 分类时从 63 次降至 3 次,约 **21x**)
- 相似度检查在 n=1000 时从 ~4.5s 降至 ~600ms(约 **7.5x**)
- 批量删除响应时间减少 1s(移除无意义延迟)
- 定时清理任务不再无限制并发,避免压垮 reconciler
- Excel 导入和 AI 输出增加大小校验,防止 OOM

**用户已确认的决策**:
- 移除 `SimilarityCheckServiceImpl:351` 的 1 秒硬延迟(无明确用途)
- 倒排索引在 `n≥500` 时自动启用
- 定时清理任务用 `flatMap(concurrency=16)` 限并发

### 2. P-2: 相似度算法倒排索引优化

**文件**:
- [src/main/java/top/puresky/hitokotohub/service/similarity/SimilarityPairFinder.java](file:///c:/Users/19002/Documents/Trae/plugin-hitokoto-hub/src/main/java/top/puresky/hitokotohub/service/similarity/SimilarityPairFinder.java)
- 新建 `src/test/java/top/puresky/hitokotohub/service/similarity/SimilarityPairFinderInvertedIndexTest.java`

**改动要点**:

1. **保留现有 `find()` 方法作为入口**,内部根据 `n` 分派:
   ```java
   private static final int INVERTED_INDEX_THRESHOLD = 500;

   public static List<SentencePair> find(List<SentenceProfile> profiles,
                                           String algorithm, double threshold) {
       int n = profiles.size();
       if (n < INVERTED_INDEX_THRESHOLD) {
           return findBruteForce(profiles, algorithm, threshold);
       }
       return findWithInvertedIndex(profiles, algorithm, threshold);
   }
   ```
   原 `find` 方法体重命名为 `findBruteForce`(纯重命名,逻辑不变)。

2. **新增 `findWithInvertedIndex` 方法**:
   - 预处理阶段与暴力法相同:计算 `tfVectors`、`tokenSets`、`tfidfVectors`
   - 构建倒排索引:`Map<String, BitSet>` 或 `Map<String, IntArraySet>`,key=bigram,value=包含该 bigram 的句子索引集合
   - 遍历每个句子 `i`,收集所有 `j > i` 且与 `i` 共享至少一个 bigram 的候选句子
   - 仅对候选对计算相似度,过滤阈值
   - 排序逻辑不变

3. **正确性保证**:两算法结果集理论等价(相似度 > 0 ⟺ 共享至少一个 bigram),新增等价性测试验证。

4. **算法层保持零 Spring 依赖**:所有代码在 `service.similarity` 包内,仅依赖 JDK + `SentenceProfile`/`SentencePair` record。

**复用现有工具**:
- `TextSimilarityCalculator.tokenizeToSet` / `computeTfVector` / `computeIdf` / `computeTfidfVector` / `cosineSimilarity` / `jaccardSimilarity` 全部复用
- `SentenceProfile` / `SentencePair` 不变

**预估收益**:n=1000 时配对数从 ~50 万降至 ~5 万(10x),整体耗时约 5-8x。

### 4. P-5: 移除 synchronized 方法内的 block() 调用

**文件**: [src/main/java/top/puresky/hitokotohub/scheduled/StatsCleanupScheduler.java](file:///c:/Users/19002/Documents/Trae/plugin-hitokoto-hub/src/main/java/top/puresky/hitokotohub/scheduled/StatsCleanupScheduler.java#L73-L99)

**改动要点**:

当前 `scheduleAiGenerateTask()` 是 `synchronized` 方法,内部调用 `resolveAiCron()` 时执行 `settingConfig.getAiConfig().block()`(L89),持锁阻塞 I/O。

**重构方案** — 配置缓存 + 事件驱动更新:
1. 新增 `private volatile String cachedAiCron;` 字段
2. `resolveAiCron()` 改为同步读缓存,无 I/O:
   ```java
   private String resolveAiCron() {
       String cron = cachedAiCron;
       if (StringUtils.hasText(cron)) {
           return cron;
       }
       return DEFAULT_AI_CRON;
   }
   ```
3. 新增 `refreshAiCronConfig()` 方法(reactive),在 `onPluginConfigUpdated` 事件和启动时调用,异步读取配置并更新 `cachedAiCron`
4. `scheduleSimilarityCheckTask` 同理处理(已有 reactive 读取,但内部仍有 `.subscribe()` fire-and-forget,改为先刷新缓存再调度)

**注意**:`scheduleSimilarityCheckTask` 当前已是 reactive(L247-260),但其 `settingConfig.getSimilarityConfig().flatMap(...).subscribe()` 模式意味着任务注册是异步的 — 如果 `configureTasks` 同步返回后立即有任务触发,可能配置还未加载完成。重构后用缓存可保证同步可用。

### 5. P-6: 定时清理任务限制删除并发

**文件**: [src/main/java/top/puresky/hitokotohub/scheduled/StatsCleanupScheduler.java](file:///c:/Users/19002/Documents/Trae/plugin-hitokoto-hub/src/main/java/top/puresky/hitokotohub/scheduled/StatsCleanupScheduler.java#L142-L148)

**改动要点**:

两处 `Flux.fromIterable(...).flatMap(client::delete)`(L142 和 L192)改为 `flatMap(client::delete, 16)` 限制并发为 16。

```java
// before
return Flux.fromIterable(records.subList(0, deleteCount))
    .flatMap(client::delete)
    .count()...

// after
return Flux.fromIterable(records.subList(0, deleteCount))
    .flatMap(client::delete, 16)
    .count()...
```

用户已确认选择 `flatMap(concurrency=16)`,平衡速度与 reconciler 压力。

**注意**:`SimilarityCheckServiceImpl.deleteSentencesSerially`(L341)已用 `concatMap`(串行),本项目硬约束"批量删除非最优句子串行避免乐观锁冲突"针对的是 Sentence 删除。CategoryViewRecord 和 AiGenerateLog 的删除不会触发 SentenceReconciler,因此限并发 16 是安全的。

## 风险与兼容性

| 风险 | 缓解措施 |
|---|---|
| 倒排索引结果与暴力法不一致 | 新增等价性测试(500+ 句子断言结果集相同) |
| Overview 全量加载 CategoryViewRecord | 默认 maxKeep=1000,内存安全;大量数据时由 StatsCleanupScheduler 定期清理 |
| 配置缓存导致 Cron 不及时更新 | `onPluginConfigUpdated` 事件同步刷新缓存;启动时也刷新一次 |
| Excel 大小限制影响现有导入 | 10MB 足够覆盖正常使用(500 句子 × 200 字 ≈ 100KB) |
| AI 输出限制截断有效内容 | 512KB 足够 1000 条句子;单条内容超 500 字会被截断(与 SentenceConsoleEndpoint 一致) |
